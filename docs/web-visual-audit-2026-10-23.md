## 보강한 검사가 놓친 이유와 확인

P1, P2, P4는 이전 두 실행에서 자동 검사를 모두 통과했고 화면 판독 역할이 찾았음. 이유는 세 가지임. 생성 글자 검사가 `counter()` 숫자를 건너뛰었고, 입력 칸 글자는 표시 층이 아니라 입력 칸 자체의 글자라 표시 층 대비를 재는 검사가 없었고, `::selection`은 검사 대상이 아니었음.

보강한 검사를 수정 전 스타일에서 돌려 실제로 걸리는지 확인함. 같은 검사를 git HEAD의 `styles.css`, V1·V2만 고친 스타일, 현재 스타일에 대해 어두운 모드와 밝은 모드로 돌림(3개 화면 상태와 책 진입 화면).

| 스타일 | 어두운 모드 실패 | 밝은 모드 실패 |
|---|---|---|
| git HEAD | 19건(숫자 배지 17건, 고른 표시 1건, 선택 색 1건 3.99:1) | 0 |
| HEAD에 V1·V2만 고침 | 19건(같음) | 0 |
| 현재 | 0건(선택 색 5.99:1) | 0 |

숫자 배지 17건은 서로 다른 배지 10개를 화면 상태 4곳에서 센 값(사용 순서 4, 검토 기록 3, 책 진입 사용 순서 3)이며 측정값은 전부 2.15:1, 고른 표시는 1.36:1로 화면 판독 결과와 같음.

밝은 모드가 바뀌지 않았는지 두 가지로 확인함.

| 계산된 스타일 비교 | git HEAD의 `styles.css`(경로 가로채기로 서빙)와 현재 스타일로 같은 화면 5곳(첫 화면, 건너뛰기 링크 초점, 표현을 고른 쉬운 결과, 전문가 모드 전체 펼침, `/web/?entry=book`)을 그려 요소 322~1,462개의 색, 테두리, 윤곽, 그림자, 변환, 위치·크기와 `::before`·`::after`를 비교. 밝은 모드 차이 0. 어두운 모드 차이는 `a.skip-link`, `p.book-entry-kicker`, 숫자 배지(`li`, `label`의 `::before`), 고른 표시(`mark.posting-mark.is-active`)뿐 |

## 긴 화면 캡처 문제 (P3)

화면 판독 역할이 데스크톱 모두 펼침 캡처의 y 약 16,400px 아래가 비어 있다고 알림. 같은 상태를 전체 화면 캡처(1366x24934)와 스크롤 위치별 화면 크기 캡처 28개로 찍어 비교해 재현함.

- 전체 화면 캡처는 y 16,200부터 22,500까지 8개 구간에서 스크롤 캡처와 달랐음. y 17,100에서 전체 화면 캡처는 흰 화면이고 스크롤 캡처에는 '정보·설명과 접근' 질문 묶음이 그려져 있음.
- 원인은 레이아웃이 아니라 Chromium의 전체 화면 캡처 한계(약 16,384px)로 판단함. 스크롤 캡처에서는 같은 구간이 모두 그려짐.
- 검사 도구는 이제 15,000px보다 긴 화면을 스크롤 위치별 캡처로 찍고 구간마다 빈 화면인지 검사함. 이번 실행에서 12곳, 338개 구간 모두 비어 있지 않음.
