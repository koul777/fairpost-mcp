## 문제

`is_excluded`(웹 엔진은 `isExcluded`)는 후보 앞뒤 `window`자를 `text[left:right]`로 잘라 그 조각에서 제외
term을 찾았음. 정규식은 조각의 시작과 끝을 글의 시작과 끝으로 보므로 아래처럼 판정됨.

| 구성 | 창으로 자른 조각에서 | 영향 |
|---|---|---|
| `$` | 창 끝에서 참 | 줄이 이어져도 줄 끝으로 판정해 제외함 |
| 부정 lookahead `(?!…)` | 창 밖의 부정어ㆍ거절어를 못 봄 | 거절 표현이 창 밖에 있으면 제외함 |
| 양의 lookahead `(?=…)` | 창 밖의 글을 못 봄 | 필요한 글이 창 밖에 있으면 제외하지 않음 |
| `^`, lookbehind | 창 시작을 글 시작으로 봄 | 앞 글자를 못 보고 판정함 |

2026-10-20 공백 사다리(실제 제한 82건의 공백 자리마다 공백ㆍ탭 1~300개를 넣은 29,456건)에서 실제 제한
844건이 표시되지 않았고(main은 20건), 그중 66건은 제외 구조 안에 공백 40개 이상을 넣은 형태로 PR #15보다도
적게 표시됨.

## 설계

판정 규칙: term 일치는 창 `[left, right]` 안에서 시작하고 끝나야 함. 일치를 고르는 앞뒤 확인(lookahead,
lookbehind, `^`, `$`)은 창 밖의 실제 글을 봄.

| 단계 | Python (`_window_spans`) | JS (`windowHit`) |
|---|---|---|
| 시작 위치 찾기 | `regex.search(text, pos, limit)`, `limit = right + EXCLUDE_LOOKAHEAD` | 전역 정규식, `lastIndex = pos`, `text.slice(0, limit)`에서 `exec` |
| 그 위치의 일치 | `regex.match(text, start)` (글 전체) | sticky(`y`) 정규식, `lastIndex = start`, 글 전체에서 `exec` |
| 일치가 창 끝을 넘을 때 | `(?:term)(?=[\s\S]{k})`로 같은 시작에서 다시 찾음. `k = limit - right`. 맨 앞 전역 인라인 플래그(`(?i)` 등)는 묶음 앞에 둠. 묶을 수 없는 term(verbose, 컴파일 실패)은 `regex.match(text, start, right)` | 같은 정규식을 sticky로 만들어 `text.slice(0, limit)`에서 `exec`. 만들 수 없으면 `text.slice(0, right)`에서 `exec` |
| 다음 위치 | 일치 끝(빈 일치면 다음 글자), 일치가 없으면 다음 글자 | 같음(다음 코드 포인트) |

- 왼쪽: Python `pos`와 JS `lastIndex`는 글을 자르지 않으므로 lookbehind는 창 앞 글자를 보고, `^`는 글 맨
  앞에서만 참임.
- 오른쪽: 그 위치의 일치는 글 전체에서 다시 맞춰 보므로 부정 lookahead와 `$`는 글 끝까지 봄. 창으로 자른
  조각에서는 `$`가 창 끝에서 참이었지만 이제는 실제 줄 끝ㆍ글 끝에서만 참임.
- 탐욕 수량자(`[^\r\n]{0,80}`, `[\s\S]{0,700}` 등)는 글 전체에서는 창 밖까지 늘어날 수 있음. 이때 같은 시작에서
  창 안에서 끝나는 첫 일치를 다시 찾아, 앞뒤 확인이 없는 term은 창으로 자른 조각과 같은 일치를 냄. 시제품
  비교에서 이 재시도를 빼면 train 1건(Q-DIST-010 #0)의 판정이 바뀌었음.
- 보기(view): 정규식 term은 글에 호환 문자ㆍ폭 없는 문자가 있으면 정규화한 보기를, 글자 그대로 term은 원문과
  형태소 보기를 읽음(`_scan_matches`와 같음). 보기는 글 전체로 만들고(캐시 공유), 창은 보기 위치로 옮김
  (`bisect`, JS는 이진 탐색). 보기의 빈 일치는 예전처럼 버림.
- 사전 검사: term에 반드시 들어가는 글자가 창 안(`text.find(lit, left, right)`, JS `text.slice(left, right).includes`)에
  없으면 정규식을 실행하지 않음. 필수 글자는 소비하는 부분에서만 고르므로 결과는 그대로임. 처음 커밋(`43674ea`)의
  JS는 `indexOf(lit, left)`로 창 밖 글 끝까지 훑어 긴 공고에서 후보 수 곱하기 글 길이가 됐음(독립 검토 지적).
- 인라인 플래그: Python은 전역 인라인 플래그를 패턴 맨 앞에서만 받으므로, 처음 커밋은 `(?i)`로 시작하는 term이
  재시도 경로에서 `re.error`로 멈췄음. 지금 `data/`에는 그런 term이 없고 `data/local_rules.yaml`로만 들어올 수 있음.
  웹 번들은 `data/`로만 만들고, JS `RegExp`는 `(?i)`를 받지 않아 예전에도 쓸 수 없음.

### 범위 제한 `EXCLUDE_LOOKAHEAD = 1024`의 근거

- 시작 위치를 글 끝까지 찾으면 후보마다 글 길이만큼 훑어 긴 공고에서 후보 수 곱하기 글 길이가 됨. 시작 위치
  찾기는 창 끝에서 1024자까지만 봄.
- 시작 위치 찾기에서 놓칠 수 있는 것은 잘린 글에서만 거짓이 되는 확인이 1024자 너머의 글을 봐야 성립하는
  일치뿐임. 지금 term에서는 양의 lookahead(AGE-002 #9ㆍ#10, SEX-001 #2)와 부정 lookahead 안의
  `(?![가-힣])`(Q-DIST-005 #3, Q-DIST-017)가 해당함. 부정 lookahead와 `$`는 잘린 글에서 더 쉽게 성립하므로
  시작 위치를 놓치지 않고, 찾은 시작 위치의 일치는 글 전체로 다시 확인함. 놓치면 제외하지 않는 쪽(표시)이 됨.
- 창 끝을 넘는 일치의 재시도는 앞뒤 확인을 1024자까지만 봄. 확인 정규식 `(?=[\s\S]{k})`가 남은 글 길이만큼
  검사하기 때문임.
- 1024는 공백 사다리의 최대 300자와 제외 구조 안 거리(공백을 뺀 40자 안팎)를 넉넉히 덮음. train 2,316건에서
  시작 위치 찾기가 창 끝 너머까지 훑은 것은 1,374회(시제품 계측, 정규식 실행 2,653회 중)였음.

## 남은 한계

- `EXCLUDE_LOOKAHEAD` 너머: 양의 lookahead가 창 끝에서 1024자 넘게 떨어진 글을 봐야 성립하는 일치는 찾지
  않음(표시 쪽). 창 끝을 넘는 탐욕 일치를 다시 찾을 때는 앞뒤 확인도 1024자까지만 봄. 이 경로에서 거절어가
  1024자 너머에 있으면 제외할 수 있음(숨김 쪽).
- 시간: 찾은 일치의 앞뒤 확인이 긴 공백을 끝까지 읽으므로, 긴 공백 앞에 후보가 몰리면 시간이 공백 길이와 후보
  수에 비례해 늘어남. 후보 400개와 공백 10만 개 합성 입력에서 Python 제외 판정이 약 0.02초에서 약 0.07초.
