# FairPost 엔진 성능 벤치마크

`tools/benchmark_engine.py`는 FairPost Python 엔진의 개발 환경 기준 처리 성능을
재현 가능한 방식으로 관찰하는 도구다. 결과는 운영 환경의 SLA나 용량 보장이
아니며, 규칙 또는 매칭 구현이 바뀌었을 때 같은 조건의 추세를 비교하기 위한
근거 자료다.

## 실행

기본값은 `.corpus-prd/train/records.jsonl` 전체를 한 번 예열하고 세 번
측정한다.

```powershell
python tools/benchmark_engine.py
```

입력과 반복 조건은 명시적으로 조정할 수 있다.

```powershell
python tools/benchmark_engine.py `
  --input .corpus-final/train/records.jsonl `
  --warmup 1 `
  --repeats 5 `
  --max-records 500 `
  --output reports/engine_performance.json
```

- `--warmup`: 측정 전에 전체 선택 레코드를 실행하는 횟수이며 기본값은 1이다.
- `--repeats`: 선택 레코드를 측정하는 횟수이며 기본값은 3이다.
- `--max-records`: 입력 순서상 앞에서부터 측정할 최대 레코드 수다. 생략하면
  전체 입력을 사용한다.

## 데이터 경계와 개인정보 보호

도구는 경로에 정확한 `train` 구성 요소가 있는 JSONL 파일만 허용한다.
`holdout`, `test`, `dev`, `evaluation` 계열 경로는 실행 전에 거부하므로 봉인
평가 자료가 성능 실험에 섞이지 않는다.

보고서에는 공고 원문, 레코드 ID, 기관명이나 기관별 결과, 개별 레코드 타이밍을
기록하지 않는다. `input.sha256`은 실제 선택된 원문을 입력 순서와 UTF-8 바이트
길이까지 포함해 묶은 SHA-256이다. 따라서 입력 동일성을 검증할 수 있지만 보고서로
원문이나 식별자를 복원할 수는 없다.

## 측정 방법

엔진과 규칙 로딩은 측정에서 제외한다. 각 `engine.check()` 호출의 직전과 직후를
단조 증가 시계인 `time.perf_counter()`로 측정한다. `elapsed_seconds`는 모든
개별 호출 시간의 합이다. 처리량은 반복마다 따로 계산해 `metrics.repeat_postings_per_second`에
반복 순서대로 남기고, 대표값 `postings_per_second`는 이 반복별 처리량의 중앙값이다
(`configuration.throughput_aggregation`: `median_of_repeats`). 한 번의 반복이
일시적인 부하(메모리 압박, 다른 프로세스)로 느려져도 대표값은 흔들리지 않는다.
`pooled_postings_per_second`는 이전 대표값 정의(전체 측정 호출 수 ÷ `elapsed_seconds`)이며,
`throughput_aggregation`이 없는 이전 보고서의 `postings_per_second`가 이 값이다.
반복별 값이 크게 갈리면 측정 중에 부하가 있었다는 뜻이므로 다시 측정한다.
지연 시간은 모든 반복의 전체 표본에 대해 밀리초 단위의 최솟값, 평균, p50, p95,
p99, 최댓값으로 집계하며 백분위는 nearest-rank 방식을 사용한다. 집계 순서와 반올림 규칙은
고정돼 있지만 운영체제 부하, CPU 전원 상태, Python 버전에 따라 실측값은 달라질
수 있다.

보고서는 현재 `ruleset_version`, `matching_version`, Python 구현과 버전, 운영체제,
CPU 아키텍처, 입력 해시와 건수, 예열·반복 설정을 함께 남긴다. 서로 다른 보고서를
비교할 때는 이 조건들이 같은지 먼저 확인해야 한다.

## 결과 해석

`reports/engine_performance.json`(2026-10-13 현재 규칙으로 재측정)은 단일 개발 장비에서 얻은 관찰값이다. 다음과 같은
주장은 이 보고서만으로 할 수 없다.

- 동시 사용자 수 또는 서버 처리 용량
- 네트워크, MCP 전송, 웹 렌더링을 포함한 종단 간 지연 시간
- 특정 하드웨어에서 보장되는 최대 지연 시간
- 운영 SLA 또는 규제 준수 성능

운영 용량을 판단하려면 대상 배포 환경에서 동시성, 장시간 부하, 메모리, 오류율을
별도로 측정해야 한다.

## 2026-10-11 엔진 속도 개선 기록

2026-10-09부터 10-10까지 적용한 탐지 수정 이후 Python 엔진은 10-04 시점보다 약 31% 느려졌다. 같은 PC에서 같은 레코드로 측정한 결과다. 웹 엔진은 Python보다 약 3배 느렸다. 이번 작업은 속도만 개선하는 리팩터링이다. 결과는 한 바이트도 달라지지 않았고, `ruleset_version`도 그대로 유지했다.

### 변경 내용

- `core/morph.py`
  - 바뀌지 않는 문자에 대해서는 문자별 NFKC 및 오프셋 검사를 건너뛰는 빠른 경로를 추가했다.
  - 형태소 치환을 단일 정규식 패스로 바꿨다.
  - 패턴마다 리터럴 사전 필터를 두어 매칭될 수 없는 정규식을 건너뛴다.
  - 문자 단위로 정규화하는 방식은 그대로다. 문자열 전체에 NFKC를 적용하지 않으므로 분해된 자모가 합쳐지지 않는다.
- `core/extractor.py`: 순수 헤딩 보조 함수를 메모이제이션했고, 호출마다 계산하던 상수를 import 시점에 한 번만 계산한다.
- `web/engine.js`
  - 문자별 정규화 결과와 패턴별 정규식을 캐시한다.
  - 헤딩 별칭 조회는 미리 계산한 맵으로 처리한다.
  - 오프셋은 typed array로 보관한다.
  - 서로게이트 쌍은 이전과 똑같이 처리한다.
- `tools/benchmark_engine.py`: 대표 처리량은 반복별 처리량의 중앙값(`median_of_repeats`)이다. 이전 정의는 `pooled_postings_per_second`로 남겼다.

### 결과

`.corpus-final` train 레코드 500건을 같은 PC에서 3회 반복 측정한 중앙값이다.

| 엔진 | 시점 | 처리량(건/초) | p50 | p95 | 최댓값 |
|---|---|---|---|---|---|
| Python | 변경 전(`08e285f`) | 210.4 | 2.70 ms | 12.98 ms | 56.1 ms |
| Python | 변경 후 | 576.9 | 0.93 ms | 4.38 ms | 33.2 ms |
| 웹(Node V8) | 변경 전 | 72.7 | 8.4 ms | 39.1 ms | 약 98 ms |
| 웹(Node V8) | 변경 후 | 약 1,090 | 0.60 ms | 2.27 ms | 약 6.6 ms |

Python은 약 2.7배, 웹 엔진은 약 15배 빨라졌다. 웹 엔진은 브라우저가 사용하는 것과 같은 `web/data.js`와 `web/engine.js`를 로드하는 Node.js 스크립트로 측정했다.

### 동일성 검증

- 테스트와 `examples/`에 있는 공고 형태의 문자열 전체, `.corpus-final` train 2,310건, `.corpus-private-open` train 2,100건, `.corpus-prd` train 420건, 합계 6,022개 입력에 대해 전체 결과를 해시로 비교했다. 결과에는 finding 오프셋, 슬롯 근거, 질문 순서가 포함된다. 변경 전과 비교한 결과 달라진 결과는 0건이다.
- `verify_web_parity.py`로 2,310건의 레코드를 검사한 결과 웹과 Python 사이의 불일치는 0건이다.
- 새 테스트는 다음과 같다.
  - `tests/test_morph_fast_paths.py`: 모든 코드 포인트와 적대적 문자열에 대해 새 코드를 이전 구현의 사본과 비교한다.
  - `tests/test_web_engine_fast_paths.py`: 적대적 문자열에 대해 웹 엔진을 Python과 비교하며, 캐시가 비어 있는 경우와 채워진 경우를 모두 확인한다.
  - `tests/test_extractor_helpers.py`: 메모이제이션한 보조 함수를 검사한다.

### 측정 시 주의점

변경 전에 커밋되어 있던 `reports/engine_performance.json`은 50.1 postings/s를 기록했다. 그 실행은 PC의 메모리가 부족한 상태에서 이루어졌으므로 실제 성능보다 낮게 나온 값이다. 이번 작업 중 근거용 벤치마크를 처음 실행했을 때는 값이 두 단계로 갈렸다. 처음 두 반복은 583.8과 590.4 postings/s였지만, 나머지 세 반복은 약 296~307이었다. 그 시점에 다른 프로그램이 CPU를 쓰고 있었기 때문이다. 부하가 없는 상태에서 다시 실행하자 반복별 값은 535.7~556.7이었고, 중앙값은 551.7이었다. 이 실행 결과를 근거로 채택했다. 반복별 값이 크게 갈리면 위 측정 방법 절에서 말한 대로 다시 측정한다.

### 남은 병목

Python에서는 남은 시간의 대부분이 정규식 스캔(`morph._collect_matches`) 안에서 쓰인다. 이보다 더 줄이려면 패턴을 통합해야 하며, 이는 별도의 설계가 필요하다.

## 2026-10-13 통합 검증의 관찰

통합 후보(`…f84dcd7e017d`)와 작업 시작 기준(`…b5cea04dd38f`)을 같은 장비·Python 3.12.7·
train 500건·예열 1회·측정 5회로 순서를 바꿔 비교했다. 입력 해시는 두 경우 모두
`551cd8997556d05520a2e47b224b2aecae96fa0ea52bb3b48d507d6a72faeb2e`다.

| 실행 순서 | 기준 처리량 중앙값 | 통합 후보 처리량 중앙값 |
|---|---:|---:|
| 기준 → 통합 | 176.899건/초 | 161.549건/초 |
| 통합 → 기준 | 173.481건/초 | 153.849건/초 |

기준 코드도 과거의 551건/초보다 느리게 측정됐으므로 그 큰 차이를 이번 변경 때문이라고
볼 수 없다. 같은 세션에서는 통합 후보의 추가 비용이 약 9~11% 관측됐다. 반복별 값의
변동이 커 정확한 원인이나 안정적인 성능 수치로 단정하지 않는다.

이후 반환 안내 패턴의 중복 공백 탐색을 제거했다. 합성 공백 1천·2천·4천·8천 자에서
해당 정규식의 처리 시간이 약 네 배씩 증가하던 현상을 확인하고, 의미가 같은 식으로
바꿨다. 전체 엔진의 긴 공백 처리 비용은 여전히 남으며 이 수정만으로 처리량 저하를
해결했다고 주장하지 않는다. 현재 최종 버전의 측정값은 JSON 보고서를 기준으로 읽는다.
